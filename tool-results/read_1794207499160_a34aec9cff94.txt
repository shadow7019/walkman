     8→# REA
     9→
    10→Use REA when a claim depends on a shipped binary or package, decompilation,
    11→requested runtime evidence, or comparison with
    12→behavior not established by available source. For ordinary analysis of a
    13→complete source repository, use normal repository tools and do not run REA
    14→readiness or provider commands.
    15→
    16→## Connect only when needed
    17→
    18→Installing this skill supplies instructions; it does not register the REA MCP
    19→server, install analysis engines, or add tools to an already-running agent.
    20→The exception is a Claude Code or Codex plugin install: the plugin bundles
    21→this skill and registers its own `rea` server, outside the state that
    22→`rea setup` and `rea doctor` manage.
    23→
    24→If REA tools are available and their registration is not known to be stale,
    25→proceed directly to the target. Do not run diagnostics or setup before every
    26→investigation. Use the connected server's actual tool list and input schemas;
    27→a skill installed from repository main may describe capabilities absent from
    28→an older npm release. Keep complete inline Evidence when that server does not
    29→advertise retained references.
    30→
    31→If tools are absent, a call is blocked by the client, or a required provider is
    32→unavailable, read [connection and recovery](references/connection-and-recovery.md).
    33→Diagnose the observed blocker, continue useful supported work, and resume the
    34→original task after repair. Client approval, shell PATH, registration and engine
    35→availability have different remedies; avoid repeating setup for all of them.
    36→If the host times out without a REA result, do not repeat the unchanged call or
    37→assume work stopped. Read the recovery guide's deadline distinction before retrying.
    38→If the MCP connection drops, retry that call once only when it is safe to
    39→repeat or known not to have started. If it may already have changed the
    40→target, or it fails again, tell the user and ask them to restart the MCP
    41→client. If REA could not start its connection, retry once, then tell the user
    42→and ask them to restart the MCP client. Do not retry a startup failure that
    43→returns the same unchanged result. For plugin installs, follow
    44→[plugin recovery](references/connection-and-recovery.md#rea-installed-as-a-client-plugin).
    45→For setup-owned registrations, run `rea doctor` when REA could not start
    46→or tools stay missing after that restart. For `cleanup_incomplete`, a retryable
    47→capacity limit, or `configuration_invalid`, follow the recovery guide's ladder
    48→before asking for a restart. Read that guide before a second repair attempt.
    49→
    50→Choose the installation owner before repairing registration. Plugin installs use
    51→[plugin recovery](references/connection-and-recovery.md#rea-installed-as-a-client-plugin);
    52→only setup-owned registrations use the guide's
    53→[registration repair plan](references/connection-and-recovery.md#repair-registration-when-needed).
    54→A plugin-only doctor result of `missing` does not call for `rea setup`.
    55→
    56→REA setup never installs or upgrades Node.js, npm, Homebrew, Java, Ghidra, IDA,
    57→JADX, Kuna, Binwalk, or Unblob. Use existing prerequisites; do not install unrelated
    58→software to repair MCP registration. For an unsupported client, use manual stdio
    59→registration with an existing installation’s absolute runtime and entry script, or continue through the CLI.
    60→
    61→A concrete CLI fallback for an operator-supplied JavaScript tree or ASAR is:
    62→
    63→```bash
    64→npx -y rea-agents@latest analyze-javascript-application /absolute/path/to/app --json
    65→```
    66→
    67→No MCP registration or native engine is required. Read the returned Evidence,
    68→graph, limitations, and unknowns with the same care as an MCP result; the CLI
    69→returns the Evidence record directly. This fallback does not establish that
    70→MCP is configured. Native CLI tasks still require their selected engine.
    71→Prefer an existing `rea` CLI. When none is installed and REA package acquisition
    72→is within the authorized scope, use `npx -y rea-agents@latest` in its place from a
    73→trusted directory outside the target project, with absolute target paths. Managed
    74→setup binds the current installation directly; retain its runtime and package
    75→cache entry, or restore that installation before repairing its registration.
    76→For setup-owned registration, configuration repair starts with a read-only setup plan; show paths, backups and
    77→skill replacement before applying authorized changes. Preserve existing approval
    78→and target-execution boundaries.

    80→## Route the target first
    81→
    82→Choose the first tool from the target the user supplied. Use `open_binary` for
    83→active-target native or archive workflows; target-free tools take their own
    84→explicit path or endpoint and do not need it.
    85→
    86→- ASAR or extracted JavaScript/Electron tree:
    87→  `analyze_javascript_application`.
    88→- Archive/package member inventory (ZIP/APK/IPA/MSIX/AppX, DMG, or a PyInstaller
    89→  executable): `open_binary` with the supplied local path; use `inspect_artifact`
    90→  when its graph and findings help answer the question. A PyInstaller CArchive
    91→  is the application layer; the bootloader is only the native prefix. Start with
    92→  `detail: "summary"` for large inventories, then use retained inventory views
    93→  for selected member fields/pages. A complete small inventory can cost less
    94→  than extra calls and schemas. Runtime options are metadata, not files.
    95→  Compact delivery still inventories and hashes members. See the
    96→  [Python packaged applications guide](https://github.com/morluto/rea/blob/main/docs/python-packaged-applications.md).
    97→- Bun `--compile` executable: `open_binary`, then `inspect_artifact`; the Bun
    98→  module graph is the application layer. Extract stored modules and analyze the
    99→  JavaScript. See [Bun standalone executables](https://github.com/morluto/rea/blob/main/docs/bun-standalone.md).
   100→- Apple app plist, Interface Builder, asset catalog, or keyed archive resources:
   101→  `open_bundle_resources`, then the selected resource tool. This does not
   102→  require `CFBundleExecutable` or a deep provider. Resource sessions have no
   103→  executable digest or binary snapshot; use `open_binary` for native code.
   104→- Android APK code, classes, methods, or incoming references:
   105→  `inspect_android_package`, then focused Android tools when advertised.
   106→  Archive member inventory still uses the archive route above.
   107→- Managed PE/CLI assembly: `inspect_managed_artifact`.
   108→- Firmware image: `inspect_firmware_regions` when advertised. Use
   109→  `extract_firmware` when extraction is requested, with a caller-selected new
   110→  absolute output directory. These tools use caller-supplied Binwalk/Unblob on
   111→  Linux; see the [firmware guide](https://github.com/morluto/rea/blob/main/docs/guides/firmware/firmware-analysis.md).
   112→- ESP32-family app or bootloader image (`0xE9` magic): `inspect_artifact`
   113→  without a provider; see the ESP section of `references/native-and-artifacts.md`.
   114→- .NET NativeAOT PE/ELF: native Ghidra analysis. Native code can yield pseudocode;
   115→  consult the NativeAOT workflow in `references/native-and-artifacts.md` for
   116→  optional metadata recovery and its supported host/layout boundary.
   117→- Native program behavior, live calls, instrumentation, or command-run effects:
   118→  choose the matching [native runtime workflow](references/runtime-observation.md#native-runtime-questions).
   119→  `open_binary` and `trace_native_values` establish static facts; they do not
   120→  observe execution. Runtime tools have distinct launch, attach, mutation and
   121→  cleanup effects, and do not require a preliminary static session unless their
   122→  own contract says so.
   123→- User-owned browser page already open: `list_browser_targets`.
   124→- Passive traffic capture of a SPA: the default scope is the page's own origin,
   125→  and data APIs usually live on another origin. Discover API origins from
   126→  absolute URLs in loaded bundles or script text via JavaScript analysis tools
   127→  (another passive capture without those origins still scopes to the page
   128→  origin, and `completeness.excluded` counts lack URLs). Pass both the page
   129→  origin and those API origins in `allowed_origins` — the list replaces the
   130→  default scope — and read `completeness.excluded` before reporting that an
   131→  API is absent. For long captures with body shapes, use
   132→  `export_evidence_bundle` instead of expecting an inline result.
   133→- Browser action the agent must perform (click, type, navigate):
   134→  `capture_browser_scenario` with declared actions. See
   135→  [runtime observation](references/runtime-observation.md) for connect/launch
   136→  and the focused follow-up browser tools.
   137→- Agent environment (AgentEnv bundle) of a web application: read
   138→  [environments](references/environments.md) before recording; it records with
   139→  `capture_browser_scenario` and writes the bundle with `export_environment_bundle`.
   140→- Task for a desktop application's exported environment, from a
   141→  `capture-desktop-application` folder: read
   142→  [desktop application tasks](references/environments.md#tasks-for-a-desktop-application-environment).
   143→- Environment of a Linux desktop app with a task, from a request such as
   144→  "build me an Inkscape environment where the agent changes a poster's
   145→  headline": read [desktop builds](references/desktop-build.md). You drive the
   146→  app on a build computer from `start_build_computer`, then export and witness.
   147→- Fiddler Everywhere traffic or a native `.saz` capture: read the
   148→  [Fiddler workflow](references/runtime-observation.md#fiddler-everywhere-traffic-debugging).
   149→  Inspect saved SAZ with `inspect_web_network_capture` and `format: "saz"`;
   150→  connect Everywhere's separate MCP server for live traffic.

   152→  original record ordinals when useful; inspect producer fields and byte/number

   154→  old-generation heap is `REA_CAPTURE_DECODER_OLD_GENERATION_MIB` (default 192 MiB,

   158→  profile and credential exclusions. Qlog support starts with aioquic 1.5.0
   159→  JSON 0.3; stream coverage and endpoint loss declarations do not recover bodies
   160→  or establish network loss. Prefer detail summary, then kind qlog trace/stream
   161→  pages; select one trace, stream ID and direction for contribution/range pages.
   162→  Facts retain all-recorded-events-before-selection scope. Other qlog layouts

   352→  only when core-only mapping candidates help; see the
   353→  [recorded crash guide](https://github.com/morluto/rea/blob/main/docs/guides/native/recorded-crashes.md).
   354→- PE resource type/name/language trees and static icon group references:
   355→  `inspect_pe_resources` with an explicit path. This portable operation requires
   356→  no active target or engine; opaque payloads retain file ranges and SHA-256.
   357→- PE export directories and ELF dynamic-symbol exports: `inspect_native_exports`
   358→  with an explicit path; portable, no active target or engine.
   359→- Native executable, library, or analysis database: `open_binary`, then
   360→  use focused analysis tools directly; call `binary_overview` when metadata or
   361→  inventory context is useful and available from the selected provider.

   363→For an existing IDA MCP configuration, use `open_binary` with the original
   364→input binary and `provider_id: "ida"`; do not pass an `.idb` or `.i64` database.
   365→The legacy attached profile binds the already-open GUI input by SHA-256 and
   366→leaves its database open. The modern headless profile creates and closes an
   367→owned private database without saving. Installation and registration reuse
   368→[mrexodia/ida-pro-mcp](https://github.com/mrexodia/ida-pro-mcp); see the
   369→[IDA provider guide](https://github.com/morluto/rea/blob/main/docs/providers/ida-provider.md).
   370→For migration to the separate native IDA MCP plugin, follow the guide's
   371→[legacy attached migration](https://github.com/morluto/rea/blob/main/docs/providers/ida-provider.md#migrate-a-legacy-attached-registration).
   372→Replace the upstream registration explicitly; modern mrexodia tools are not the
   373→native profile. Native attachment preserves the database but does not provide
   374→direct callers; check session availability and the guide's verification limits.
   375→Proceed directly to `analyze_function`, pseudocode, or function/string searches
   376→after opening; IDA does not supply `binary_overview`. Consult session availability
   377→when composing broader workflows. Modern direct callers and unsupported dossier
   378→facets remain unknown; live IDA results are not replayed from snapshots.
   379→
   380→With `REA_KUNA_COMMAND` configured, `provider_id: "kuna"` answers procedure
   381→lists, lookups, pseudocode, assembly and `analyze_function` from Kuna's cached
   382→whole-program export. Callers/callees use a separate body-free graph shared by
   383→the session; `xrefs` returns exact-address incoming sites and filters forwarding
   384→aliases. These queries and inventory lookups do not trigger a C export. Indirect
   385→targets remain unknown and can make relationship coverage partial. Reference
   386→caches expire on close; a fresh CLI process repeats the native reference walk.
   387→Typed references, CFG, raw-memory tools and annotations remain unsupported. A cold first
   388→answer can come from a single-function run (its limitations say so); assembly
   389→waits for the export. For pseudocode and assembly, `raw_result.source` names the
   390→cached `.c`/`.asm` file and byte span, which you may search directly instead of
   391→calling per function. See the
   392→[Kuna provider guide](https://github.com/morluto/rea/blob/main/docs/kuna-provider.md).
   393→
   394→If the user says only "my app" without a name, path, or target already selected
   395→for this task, ask which app before searching for artifacts. Paths in unrelated
   396→saved reports and nearby test fixtures do not select the user's target. Resolve
   397→an actual human-readable app name to one clear installed artifact when possible;
   398→ask when matches are ambiguous. Never choose an example app on the user's behalf.
   399→
   400→In a target-free session, use `open_binary` to bind any archive/package or
   401→native target whose analysis tool operates on the active target. Do not call an
   402→unadvertised tool; inspect `binary_session` with `{}` and its
   403→`result.tool_availability` for availability reasons and remediation. Expand each
   404→group's `names` into entries, inheriting the inventory-level client requirements
   405→unless the group overrides them. The grouped name union is the complete tool
   406→inventory; use `tools/list` for canonical tool schemas. The default summary keeps
   407→each provider candidate's availability and target-support status, code and
   408→reason; `omitted_fields` lists what it leaves out. Request `{"detail": "complete"}`
   409→only when you need an unavailable candidate's remediation, provider
   410→diagnostics, candidate capability sets, or tool surface, effect and annotation
   411→flags; in those closed flag vocabularies, listed
   412→flags are true and omitted known flags are false. Provider candidate facts
   413→describe possible providers, while top-level session capabilities describe the
   414→current route and `analysis_provider_binding` names the selected provider. Do
   415→not treat those scopes as interchangeable.

   417→For editable Ghidra analysis that must survive a later agent process, select
   418→the [owned Program checkpoint workflow](references/native-and-artifacts.md#continue-editable-ghidra-analysis-across-processes)
   419→before making metadata edits. It is separate from Evidence/Unknown persistence.
   420→

   422→[deadline recovery](references/native-and-artifacts.md#ghidra-startup-deadline-recovery)
   423→before abandoning deep analysis or repeating the same cold import. The default
   424→330 seconds can be changed for new startup attempts through
   425→`update_analysis_settings` using `ghidra.startup_timeout_ms`. Changing the
   426→server's launch environment instead requires a new REA process.

   428→## Work summary-first
   429→
   430→Start with the default result and use its inline Evidence and graph context.
   431→For a JavaScript application or ELF layout whose size is unknown or large,
   432→call `analyze_javascript_application` or `inspect_binary_layout` with
   433→`"detail": "summary"`, then inspect the retained `parent_evidence_id` with
   434→`inspect_analysis_view`. Over MCP, `analyze_function` is summary-first without
   435→a flag: its default reply is the summary, and the complete dossier stays
   436→retained under `parent_evidence_id` for facet paging. Pass that ID as a
   437→`retained-evidence` reference to `compare_functions`, or inside
   438→`match_native_functions` `left_observations`/`right_observations` or
   439→`build_call_path.functions`; request `"detail": "complete"` only when the
   440→dossier must travel inline.
   441→Use the same exact-reference form in other advertised logical Evidence inputs,
   442→including optional sources, arrays and nested sources across domains. Each
   443→source can independently be inline or retained; preserve its source identity,
   444→coverage, partial facts and unknowns. A summary or inspection page has its own
   445→Evidence ID: use `normalized_result.parent_evidence_id` when the consumer needs
   446→the complete source. For portable CLI follow-ups, commands advertising
   447→`--evidence-bundle` resolve references from that selected exported bundle.
   448→See [Evidence composition](references/evidence-workflows.md) for scope and
   449→recovery; file selectors are supported only where explicitly advertised.
   450→Page module identities and select the returned `node_id` before requesting an
   451→item; a single file path can represent several graph roles. Do not repeat an
   452→identical analysis or rejected call without a changed input or resolved blocker.
   453→Recheck session state when a lifecycle change makes that status useful.
   454→Make a focused follow-up only when the
   455→returned result leaves a specific question unanswered.
   456→
   457→If MCP reports `resource_constraint` with `details.resource: "transport"`, call
   458→`inspect_analysis_view` with its reported same-session Evidence reference for a
   459→summary, one section/module, or a stable page. Use `trace_application_feature`
   460→once a seed is known, or call `export_evidence_bundle` to write the complete
   461→session to a selected path. The analysis remains complete in the ledger; avoid
   462→repeating it merely to request the same oversized response. Complete CLI JSON
   463→output also streams without a single MCP frame.
   464→
   465→When the retained parent ID is unknown, use `get_evidence_bundle` with
   466→`detail: "summary"` and exact filters for operation, target SHA-256,
   467→analysis-profile digest or canonical procedure address. Select its returned
   468→Evidence ID for the next view instead of requesting the complete bundle. When
   469→that record has no supported view (for example an annotation), read it with
   470→`detail: "records"` and an `evidence_id` filter; `missing_evidence_links`
   471→names linked sources this session does not retain.
   472→`retention: "complete-record"` means the whole record is stored; native
   473→value-flow truncation and unknown metadata remain separate. For an exported
   474→portable bundle, use `rea inspect-evidence-bundle` with JSON containing `path`,
   475→`detail: "summary"` and the same `filters`. Reading that file still requires
   476→validating its full contents within the local memory budget.
   477→
   478→A client can also truncate a successful tool result without a REA transport
   479→error. Treat that preview as incomplete; use the retained parent ID for smaller
   480→views or export when the full record is needed. Do not parse the preview as
   481→canonical JSON or repeat the producer. For JavaScript, read the
   482→[module-view and trace recipes](references/javascript-applications.md) before
   483→drilling into a large graph; a broad bidirectional trace can expand unrelated
   484→containment relationships even after summary analysis.
   485→
   486→Every conclusion must distinguish observations, inferences, and unknowns. Cite
   487→Evidence IDs, preserve limitations and incomplete coverage, and never imply
   488→that static analysis observed execution. Runtime requests execute the declared
   489→target and lifecycle; do not broaden the target or action beyond those fields.
   490→
   491→Within the user's requested investigation, call available analysis tools
   492→directly. REA does not require permission grants or per-call approval flags.
   493→The agent client can independently require approval. Follow the declared request
   494→scope and the host's actual access requirements; use the recovery guide for an
   495→observed client-policy rejection.

   497→## Plan broader investigations
   498→
   499→For requests that span multiple features or subsystems, use a staged workflow:
   500→
   501→1. Turn the request into a checklist of questions and the evidence each answer
   502→   needs. Resolve target identity and constraints from the conversation and
   503→   workspace before asking for information again.
   504→2. Inspect the current REA session, artifact identity, saved analysis database,
   505→   bookmarks, and prior evidence. Reuse matching state; do not open duplicate
   506→   sessions or repeat identical analysis.
   507→3. Start with the smallest useful overview or inventory. Follow each question
   508→   from its entry point through relevant data and state changes to its result.
   509→   Batch related operations around a specific hypothesis, then expand only when
   510→   the returned evidence leaves a concrete gap.
   511→4. Inspect relevant packaged resources and configuration alongside code when
   512→   they affect the question. Use format-aware inventory and parsers; do not
   513→   infer behavior from filenames, strings, or layout alone.
   514→5. Corroborate a conclusion with the evidence type it requires. Use runtime
   515→   observation only when static evidence cannot answer the question and the
   516→   required host runtime and OS access are available. For JavaScript behavior,
   517→   run probes against the actual app through the available browser, Electron,
   518→   or process capture workflow.
   519→6. Decompose work into independent questions. When parallel workers are
   520→   available and the questions do not depend on one another, assign distinct
   521→   scopes, point workers to existing evidence, and ask them to return sources,
   522→   conclusions, and unresolved gaps. Otherwise, work sequentially.
   523→7. Keep a concise finding ledger linking each conclusion to Evidence IDs,
   524→   confidence/evidence type, search boundary, and remaining unknowns. Update
   525→   the shared index or investigation report so later passes can reuse results.
   526→
   527→Before finishing, revisit the original checklist. Mark each question as
   528→answered, partially answered, or unresolved based on its evidence; keep
   529→bounded negative searches bounded, and do not describe a broad investigation
   530→as complete while required questions remain open.

   553→## Finish the task
   554→
   555→Explain findings in plain language and tie them to returned evidence. When the
   556→user asks to build something, use normal coding tools and separate observed
   557→behavior from design choices. Close an opened native session with
   558→`close_binary` when its engine is no longer needed. Evidence references and Unknown
   559→history remain in memory on the same MCP connection. End the investigation with
   560→`reset_investigation`; supply `save_path` to checkpoint the complete bundle before
   561→clearing. Import the saved bundle to restore original references and Unknown
   562→history in a new process. Retention is bounded and is not automatic persistence.
